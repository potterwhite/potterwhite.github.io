第二次迭代（2026）：把没有 repo 链路的厂商 SDK 恢复成 N 个 Git 子仓库

把一份被开发板厂商深度定制、repo 链路已损坏的 SDK 压缩包,恢复成可一键拉取、可正确编译、且镜像能正常运行的多仓库 SDK。

从一份经过开发板厂商深度定制过的SDK压缩包，经过整个流程（5份shell脚本+1份python脚本）的处理。

得到一份可以一键式拉取就可以正确编译出镜像，且镜像能够正常运行的深度修复的由若干（一般几十到一百多个）子仓库组成的SDK代码。

客户端拉取(完整,无省略)

repo init -u http://<server>/<GROUP>/manifest.git -b main -m default.xml --no-clone-bundle
repo sync -j8 --verify
repo start main --all
repo forall -c 'git lfs pull'

除了 repo start main --all 之外的三条都不能省。 --verify 少了会停在 (yes/always/NO) 交互提示上,默认 NO, 于是 repo hook 不执行、空目录不出现、编译可能直接失败; git lfs pull 少了只有 17G 而不是 28G,编译报文件损坏。

DDR 测试未全部跑完,但已验证 bin 可被执行,代表文件系统的基础功能正常。(假设 DDR 若有问题,可能要结合 kernel 进行调试,这属于 BSP 的工作范畴。)

一镜到底表明经过完整的代码控制的sdk是能够编译出可以正常运行的系统完整镜像的，而且这中间的验证过程是后期无感的，不需要特殊调试的，即使用者根本不需要知道到底sdk与原版被厂商毁掉repo的tarball比起来经过哪些修改。

重启可以确保从ROM->uboot->kernel的这条链路能够不止一次的被加载，而且加载成功，一次启动的成功还可能有一些底层软件的原因会被隐藏，但是如果能够两次成功启动，底层软件应是没有问题的。

二、难在哪

核心陷阱:.gitignore 并非 100% 可信

上游厂商基于RK的公版SDK进行深度的定制，然后分发给他自己的客户，作为终端客户拿到的只是一个tarball,而不是用repo管理的一个url，虽然RK原版SDK是用Repo（git）进行代码管理。 上游厂商的定制时基本完全抛弃git管理，在被.gitignore拉黑的目录里存在重要的文件。例如以下这六个头文件：

external/camera_engine_rkaiq/.gitignore/rkaiq/algos/ae/rk_aiq_algo_ae_itf.h
external/camera_engine_rkaiq/.gitignore/rkaiq/algos/af/rk_aiq_algo_af_itf.h
external/camera_engine_rkaiq/.gitignore/rkaiq/algos/asd/rk_aiq_algo_asd_itf.h
external/camera_engine_rkaiq/.gitignore/rkaiq/algos/awb/rk_aiq_algo_awb_itf.h
external/camera_engine_rkaiq/.gitignore/rkaiq/algos_camgroup/ae/rk_aiq_algo_camgroup_ae_itf.h
external/camera_engine_rkaiq/.gitignore/rkaiq/algos_camgroup/awb/rk_aiq_algo_camgroup_awb_itf.h

若不将他们放进git的白名单列表，在最终编译的时候将会直接报错“Not such file xxxx”。 可是若直接查看原.gitignore会发现，这里的所有header和source都是黑名单成员：

developer@rk3576-rk3576_ubuntu-22-04:~/sdk/linux/sdk-src/clone-aug06-v2$ cat external/camera_engine_rkaiq/.gitignore  | grep algos\/ae
rkaiq/algos/ae/linux/rv1106/aarch64
rkaiq/algos/aeis/linux/

rkaiq/algos/ae/*.h

这是无法全脚本自动化执行的内容，需要工程师以丰富的经验和快速的学习能力去判断是否要相信当前的.gitignore。 所幸的是，大部分错误并不致命，一般在编译阶段都能被发现，只要发现后加入git白名单即可编译通过。

这张表背后是两条原则。

第一:除了一眼就确定是垃圾的文件,我宁可错放,也不可错杀。

第二:我的目标是「能编译 + 能运行」,而不是「位级一致」。 因为上游开发板厂商的习惯可能也很糟糕,时常把临时文件带进最终的分发包里。正是这个思想,让我认为那 40 处 umask 差异可以不修,先看看编译会不会有问题。

四类东西各自的取舍:

  • 空目录:不敢不加。所有脚本是否都会先做 mkdir -p 并不一定,而且说不定有很多脚本会做 if [ -d ${dir_name} ],那就会报错了。
  • 大文件:LFS 需要手动 git lfs pull,这也不难,没做的话很快就会编译报错。
  • 符号链接:这里最危险,谁也不知道内部做了什么软链接。顶层目录下还可以用 manifest 来创建,子目录里的软链接就都得靠 .gitignore 来管理了,否则浩如烟海,所花之功夫甚巨。

三、做了什么判断

判断一:找对不变量

  • 我原以为本次的SDK将会是「全树都没有任何 .git」。后来纠正:.git 是有的,只是与原先的 .repo 链路断了。
  • 所以项目边界的物证不在清单里,在文件系统里。
  • .repo/manifests/*.xml 会丢、会被改坏、厂商可能根本不给;但每个子项目自己的 .git 目录一直在原地。

这里我做了一个两次任务的对比:

任务项目列表怎么来换一颗 SOC 要做什么
RK 原版 SDK(2025)逐层 cat manifest XML,手抄进代码全部重抄
厂商深度定制破坏版 SDK(2026)find -name .git,自动推导什么都不用改

需要说清楚的是:原版 SDK 我没有实际跑过。 上面是关于方法的判断,不是测试结论。

而下一版要做的,正是把这件事从「逻辑上成立」落到「结构上成立」——共性抽成一层,差异集中到另一层:

  • 共性层:不依赖清单的判据 —— .git 即项目边界、6 项断言。 这一层对所有 SDK 是同一份代码。
  • 差异层:每种 SDK 各自的应对方式 —— 清单在不在、目录布局、要放行哪些 .gitignore —— 全部收到一个地方,按上游项目名索引,而不是散在流程里。

这样加一种新 SDK 只动差异层,共性层一行不碰。也只有做到这一步,第四节那句「第二次比第一次快」才有结构上的依据,而不是一句愿望。

判断二:拒绝 git add -f

AI给过我一个最快的做法是 git add -f 把误杀的文件强行塞进去。可是我思考一会儿之后并没有同意,而是去改 .gitignore 本身。 给.gitignore这一道最佳屏障添加例外，这是一个饮血止渴的做法，这一步走出去，未来如果想回来，比重新做更难，因为要抽丝剥茧知道到底之前放过了什么文件。 「我知道有捷径,我算过代价后选择不走」，这是我的另一个工程思想。

判断三:凭据一次都不落盘

token 只作为参数传入,只在 push 的那一瞬间拼进 URL。 另外 git-lfs 会把带凭据的 push URL 打进日志,所以 3-publish-manifest.sh 只按严格白名单提交(default.xml + .gitignore)。 manifest 用 SSH 拉(不存凭据)、HTTP+PAT 推。例如：

<remote name="origin" fetch="ssh://git@<server>/<GROUP>/" />

这样就可以保证客户端进行拉取代码的时候走ssh,无感于password（gitlab目前是允许http走password验证的方法操作代码的）。

判断四:只读基线不可动摇

我有一份 readonly 的 SDK,这份代码是从 tarball 直接解压之后得到的,我手动设置为 sudo chmod a-x ./rk3576-sdk-readonly -R。 后期的 4-verify-sync.sh 就是一直对照这一份sdk作为baseline来进行比对。因为一旦被 2-rebuild.sh 操作过的sdk,至少内部的.git都会被建立为实际的.git目录。这样就与客户端repo sync下来的sdk有本质的区别了。

判断五:手动建立 main 分支

repo 的标准做法是建立一个detached的HEAD去track一个具体的commit,所以客户端最终修改完代码要提交时，就无法直接git commit & git push，因为没有branch。 我的做法是在每一个客户端拉取代码的时候增加一句代码：

repo start main --all

这样每一个仓库都有一个默认的分支，名为main了。 当然，如果你 2-rebuild.sh里用非main的分支名，那你可以改名，这样能够跟remote origin/${BRANCH_NAME} 一致，避免后期有认知负担，需要一直记得两个分支名，一个是本地分支，一个是远程分支。

附:常见故障与处置

Q1:repo init 失败,提示 fatal: ... unable to resolve "stable"

  • 原因:repo 工具默认要检出名为 stable 的 repo 源码分支,而内部镜像的主分支是 main。
  • 处置:repo init 时用 --repo-branch(或 -b)指定正确的分支名。此问题已通过在最终部署命令里带上 -b main 而规避。

Q2:repo init 失败,提示 fatal: couldn't find remote ref refs/heads/master

  • 原因:repo 默认从清单仓库的 master 分支取清单文件,而我们的清单仓库主分支是 main。

  • 处置:repo init 时用 -b(即 --manifest-branch)指定正确的清单分支名。

    repo init -u <URL> -b main

Q3:国内无代理环境下,repo init 失败,连不上 gerrit.googlesource.com

  • 原因:repo 启动器默认从 Google 下载它自己的完整程序。

  • 处置:管理员先在内部 GitLab 上建一个 repo 工具的镜像仓库(例如 <GROUP>/git-repo),用户 repo init 时用 --repo-url 指向这个内部镜像。

    repo init -u <清单URL> --repo-url=http://<server>/tools/git-repo.git ...

Q4:repo sync 失败,提示 HTTP Basic: Access denied,或被重定向到登录页

  • 原因:走 HTTP 访问私有仓库,没有提供有效的认证信息。

  • 处置一(URL 里嵌 PAT):在 repo init 的 -u 和 --repo-url 两个 URL 里都嵌入 username:PAT@。

  • 处置二(~/.netrc,推荐):在家目录建 ~/.netrc 存 GitLab 的认证信息,git 会自动读取,命令本身不用改。

    # ~/.netrc
machine <server>
login <user>
password glpat-xxxxxxxx

    最终我们切换到了 SSH 方案,此问题不再出现。

Q5:repo sync 的 Checking out 阶段失败,提示 ManifestInvalidRevisionError: revision main in ... not found

  • 原因:GitLab 上部分子项目仓库没有 main 分支(可能保留了原始的 master 等分支名),与清单文件要求的 revision="main" 不符。
  • 处置(管理员):跑一个脚本(如 migrate_sdk_intelligent_final.py),把所有子项目仓库的主分支统一重命名为 main 并推送到 GitLab。

Q6:repo sync 过程中出现大量 Invalid clone.bundle file; ignoring. 警告

  • 原因:repo 去下载 GitLab 服务器上并不存在的 clone.bundle 性能优化文件。
  • 处置(用户):repo init 时加 --no-clone-bundle,可彻底消除这个无害警告。
